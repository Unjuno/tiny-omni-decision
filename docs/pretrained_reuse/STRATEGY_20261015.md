## 現在の実行方針を一枚にまとめる

**優先するのは、小型モデルが観測・条件・候補を正しく対応付ける能力である。**
完成品は「観測表現を再利用し、条件付きの候補確率をJSONで返す、全常駐200M以下のモデル」。
95–98%は定義した各必須課題で測り、未達の課題を集計値に隠さない。

| 段階 | 作業 | 次へ進む根拠 |
|---|---|---|
| 1. 教師の能力を確認（実行済み） | 固定教師の条件対照と、表示順／ラベル割当の診断を完了。この方式の蒸留は採用しない | 条件による弱さと順序依存が確認された。TRAIN診断を製品精度とはしない |
| 2. 判断中核へ移す | 独立した構文・状態の契約を固定。正解ラベルを基準とし、教師が合格した能力だけ補助蒸留を比較 | 未知条件への改善と既存能力の保持が両立する |
| 3. 実入力へ接続 | 同じ判断を正しい状態／画像・音声・動画の特徴から比較する | 判断部分と知覚部分の失敗を分け、必要な箇所だけ改善できる |
| 4. 時間・共同入力を成立させる | 前後関係と、両入力が必要な判断を独立した場面で測る | 順序反転・入力取り違え・単独入力の対照で、必要情報の利用が確認できる |
| 5. 統合して圧縮 | 一つの実行系で品質・全常駐数・遅延を測り、その後8bit／4bitを比較 | 各課題の品質と校正を保ち、実機で容量・速度の利益が出る |

一度に動かす学習仮説は一つ。新しい比較には、変更点・独立データ・予算・採否条件を先に定める。
同じ観測済み検証集合に対する学習量・配合・温度の探索は続けない。
実装・ロード・テストの成功と、判断品質の成功を別々に管理する。

## 1. 推奨する方向

**既存の入力エンコーダーと実行基盤を再利用し、条件理解・候補の意味理解・時間情報の利用を学習する小型Decision中核へ研究を集中する。**
直近の係数調整や、同じ少数シーン上でのreadout変更を積み重ねる経路は閉じる。
次のモデル選択では「一部の分類精度」ではなく、同じ観測から条件に応じて正解を変えられるか、未知の条件と場面に移せるかを主に測る。

最終目標は変更しない。

- 全常駐モデルの量子化前パラメーター数が200M以下。
- テキスト・画像・音声・動画から判断できる。センサーは任意。
- 非テキスト入力だけでの判断と、テキスト／音声の条件を与える判断の両方を扱う。
- 任意の候補IDと説明に対する確率を返し、JSONとして利用できる。
- 事前に定義した代表的な各タスク・各モダリティで95%以上、98%を目指す。
- 同じ観測を複数の判断で再利用する。製品推論はローカルで完結する。

あらゆる未定義の問題に95–98%という保証は検証できない。汎用性は、単なる固定分類の追加ではなく、
未学習の条件表現・候補説明・組合せ・場面への転移で評価する。高得点になる問題だけを残して目標を達成したことにしない。

## 3. 進め方を修正する理由

これまでの再現性・権利・漏洩対策は再利用できる資産である。一方、部品の動作確認と小さな追試の完了が増えても、
汎用条件理解や未知の動画場面の精度には十分つながっていない。テスト件数や成果物数は品質の進捗指標にしない。

失敗の原因を「200Mでは不可能」「学習ステップ不足」「encoderが悪い」のいずれかに断定できる証拠はない。
現状では、少数の独立場面、狭い教師信号、タスクに必要な情報を落とす表現、条件と観測の対応付けが混在している。
原因ごとに次の処置が変わる診断を先に置く。

| 観測 | 次の処置 |
|---|---|
| 正しい構造化状態を診断用に渡しても条件判断に失敗 | 条件・候補の意味表現と教師信号を修正。画像encoder増強へ進まない |
| 構造化状態なら解けるが、実入力の特徴では解けない | 必要な局所・時間情報の保持、事前学習目的との適合を調べる |
| 単独入力は使えるが、共同入力が最良の単独入力を超えない | データの相補性、時刻・対応付け、融合を調べる |
| 訓練は良いが、独立場面で崩れる | 独立したデータと組合せの多様性を増やす。同じ例の反復を優先しない |
| 訓練も独立検証も低い | ラベル・最適化・表現・容量の順に小さく切り分ける |

構造化状態や正解注釈を使う診断はoracle条件として明示し、実入力モデルの精度には数えない。
診断で正解を渡す経路を製品推論へ混入させない。

## 4. 採用する設計方針

### 出力

JSONを採用する。モデルが出す候補確率を通常のコードで整形すればよく、JSONを書くための生成decoderは不要。
排他的な選択は候補間softmax、独立した複数のyes/noは個別の確率として扱う。両者を混同しない。
序数scoreは定義済みの段階に対する分布から計算する。意味のある根拠なしに、すべての値を「校正済み」と呼ばない。

```json
{
  "selected_id": "candidate_b",
  "probabilities": {"candidate_a": 0.12, "candidate_b": 0.88},
  "abstain": false
}
```

上は形式例であり実測値ではない。候補数を二つに減らすだけでは主なencoderのサイズは変わらず、元の多択問題の達成にもならない。
候補順序に対して同じIDの結果が維持される構造を優先する。既存のjoint-candidate方式は順序依存と精度低下で不採用となっており、
同じ構成を再投入しない。[既存比較](R2_JOINT_LEARNING_RESULTS_20261012.md)。

### 入力・判断中核

最初の製品候補はPath A：共有する画像／動画encoder、小型音声経路、小型の事前学習済み言語経路とDecision中核。
画像・動画では必要な局所情報と時刻を残す。音声では発話と環境音を区別する。全入力を必須の文字起こしへ変換しない。
一度作った観測表現を、任意の条件と候補の採点で再利用する。

既存の全encoder凍結は比較基準として保持する。十分な教師信号を用意しても凍結特徴側の不足が診断された場合に限り、
該当する小さなadapterや上位ブロックを一箇所ずつ適応する。永久にheadだけを変更することも、全encoderを一度に学習することも既定路線にしない。

以下は次候補の設計予算であり、完成済み構成の計測値ではない。

| 部分 | 予算 |
|---|---:|
| 画像／動画共有 | 現行VideoPrismの114.365Mを対照として維持 |
| 発話特徴 | encoderだけなら実測8.208M。decoder除去後の汎用発話理解は未証明 |
| 環境音 | 現行約1.961M |
| 条件・候補を読む言語経路 | 30M以下を設計目標 |
| 接続・時間処理・Decision中核 | 合計20M以下を設計目標 |
| 任意のセンサー経路 | 1M以下を設計目標 |
| 小計 | 約175.535M、残り約24.465Mは追加部品と仕様変更への余裕 |

元の195.42M構成には37.76MのWhisper全体が含まれる。8.208M encoder経路への置換は品質同等と確認された変更ではなく、
そのままパラメーターを差し引いて製品完成を主張しない。既存の二つの言語モデルを一つに統合することも機能確認が必要。
Embedding、接続層、例外テンソルを含め、最終的にはロードした全構成を再集計する。

### 他の二案の位置付け

- 既存の大きなDecisionモデルの直接採用：比較には有用でも200M制約を満たさないため製品候補にはしない。
- 全モダリティを一つのbackboneへ押し込むLens／重み統合：小型化の効果が必要になり、互換性と品質を示せた場合の研究候補。今の品質不足の初手にはしない。

Liquid D1の公式資料でもyes/noだけでなくchoiceとscoreを扱い、確率から構造化出力する。
公開d1-omniは約587Mで、画像と音声の同時入力や時間的動画理解をそのまま実現する比較対象ではない。
既存の[固定revision監査](R1_D1_OMNI_SOURCE_AUDIT_20261012.md)を再利用し、同じ監査を繰り返さない。
ライセンスは現在REVIEWのため、学習・蒸留・製品への組込みに自動的に使えるとは扱わない。
[公式モデルカード](https://huggingface.co/LiquidAI/d1-omni-600M)・[公式Decision仕様](https://docs.liquid.ai/lfm/models/decision-models)。

## 5. 評価とデータの優先順位

目指す初期用途は「ローカルで観測と指示を照合し、次の候補・状態を選ぶDecision部品」とする。
実機の自動操作までは今回の品質研究に含めない。用途を次の三つの能力群に分け、四つの入力モダリティを横断して評価する。

1. **条件による選択**：同じ状態に違う条件を与えると、対応する正解へ変わる。言い換え・否定・比較・候補説明を含む。
2. **知覚情報への接地**：画像の対象／関係、音声の発話／イベント、動画の状態を使って判断する。既存の固定taxonomyだけで完了しない。
3. **時間・入力間の対応**：前後・変化・順序、発話と見えている対象／出来事の対応を扱う。両入力が必要な問題で片方だけの対照を置く。

Lombardは対応付けの基準として残すが、汎用AVの中心ベンチマークにはしない。
センサーを必須にしてデータ選定を止めず、校正・時刻・正解・利用許可を確認できる実データがある場合に追加する。
新しい公開データ候補は「権利」「独立した場面数」「必要なラベル」「実ファイルへのアクセス」「狙う能力」の全てで判断する。
候補源の探索は一度に三つまでとし、同じ未解決条件を繰り返し調査しない。十分な源がなければ、その能力を未評価と明示する。

train / validation / calibration / sealed auditを用途別に分け、話者・場面・対象・元asset・正規化内容で重複を防ぐ。
既に多数回見た検証集合は回帰用として固定し、新たな汎化の証拠に使わない。
未知の条件表現、候補、組合せ、収録環境など、何を未見とするかを分割前に定義する。
最終監査は構成と選択規則を固定した後の一度に限定する。

学習は正解ラベルを中心にし、同じ観測に複数の条件、同じ条件に異なる観測、意味の近い負例を含める。
難しい例を落とさず、候補数やラベル頻度の近道を抑える。独立asset数・組合せ数と反復回数を区別する。
日本語と英語の結果は別々に記録し、未学習・未測定の言語まで対応済みとしない。

教師蒸留は第二の学習要因とする。利用可能な教師を同じ開発タスクで測定し、実際に強い能力だけを候補とする。
対象TRAIN例へのoption-logit蒸留を、正解ラベルだけの学習と同じ初期化・データ・予算で比較する。
教師の誤りを正解扱いせず、過去に失敗したembedding全体の模倣を既定にしない。未許可の教師・データを使わない。

## 6. 次の実行順序と終了条件

| 順序 | 実行すること | 得たい判断 |
|---|---|---|
| 1 | 新しい能力表と独立データの契約を一つ作る。既存baseline・利用可能な強いreference・oracle診断を同条件にそろえる | 条件理解、知覚表現、融合、データ不足のどこが主要な差か |
| 2 | 最も大きい差を狙う一つの候補を実装。既存baselineとの二条件を同じ新コーパス・予算で比較 | 新しい情報／教師信号が必要能力へ移ったか |
| 3 | 有望なら、正解ラベル学習に対するoption-logit蒸留、または診断された一箇所のadapterを別比較 | 追加費用に見合う効果か。複数変更の効果を混ぜない |
| 4 | 単独・共同・条件変更・未知条件の保持を確認し、全入力を一つの実行パッケージへ接続 | 全常駐数、実入力からJSON、再利用、校正が一緒に成立するか |
| 5 | 高精度版の品質が合格してから8bit、必要なら4bitを測る。ternaryは別研究として後置 | 容量・速度の実益と各タスクの品質保持 |
| 6 | 固定した製品候補を未使用監査セットと対象実機で評価 | 各目標の達成／未達を確定する |

最初の比較はseed17と固定した学習曲線を使う。スケジュールや上限は実測throughputから事前に定め、
実行中にデータ・設定・候補数を変更しない。別seedは有望な構成の再現性確認に限る。

研究候補の前進条件は実験前に固定する。初期案は、主対象の弱いタスクでAccuracyを3ポイント以上改善し、
集団単位の不確かさも改善を支持し、他の必須タスクを1ポイント超落とさないこと。
NLL/Brier/ECEと条件変更ペアも併記し、Accuracyだけの改善で過信や忘却を認めない。
これは次段階へ進む研究上の基準であり、95–98%という製品の合格条件を置き換えない。
必要な独立評価数が不足すればUNCERTAINとし、質問の複製で見かけの確信を増やさない。

同じ独立データ・同じ主要仮説の二つの事前比較で有用性が確認できなければ、その経路を閉じる。
新しいデータや異なる事前学習表現など、失敗原因を変える根拠がない限り第三の微調整へ進まない。
許容できる構成が見つからなければ、その条件下の結果を報告し、200M制約や難問を黙って変えない。

## 7. 作業配分と継続管理

研究作業の目安を、データ・条件／接地学習60%、能力の切り分け25%、統合・実行費用15%へ移す。
これは資源利用の実測や費用承認ではなく、優先順位の目安である。既存のローカルGPUを使い、有料計算や機材購入は行わない。

アクティブな学習仮説は一度に一つにする。新しい実験は「狙う能力」「現在値」「一つの変更」
「独立例数」「予算」「成功・打切り条件」を一枚で説明できることを開始条件にする。
変更に関係するテストと必要な再現確認を行い、変更も疑義もない同じ全検証を繰り返さない。
既存の固定成果物を参照して、過去の全処理を再実行しなくても比較できる形を保つ。

今後の報告は、モダリティ／能力ごとの品質・最低品質・条件変更ペア・未知条件・共同入力の有効性・
全常駐パラメーター・実行費用を同じ表で追う。テスト成功、モデルのロード成功、JSON出力成功は工程上の条件として別に扱う。

この戦略による現時点の製品判定は**未達**。最初の実行工程として、

5. **統合後の品質を確認して量子化する。** 8bit、必要なら4bitへ進み、各タスク・校正・

第1項の固定重みでの転移比較も実行した（第9節）。現在の検証集合に対するKL係数・
