# EgoViz unseen-session temporal correspondence plan — 2026-10-29

## Status

**Metadata split is frozen. A two-session train/development raw-data smoke has
since completed; bulk acquisition, new feature extraction, model fitting and
sealed evaluation have not started.** The smoke is documented separately in
[`R2_EGOVIZ_UNSEEN_GROUP_TEMPORAL_SMOKE_20261029.md`](R2_EGOVIZ_UNSEEN_GROUP_TEMPORAL_SMOKE_20261029.md).
This is a follow-up to the existing
EgoViz video/IMU timestamp-correspondence pilot. It excludes all 16 publisher
sessions used by that pilot and therefore creates a fresh development set for a
single, fixed-budget follow-up. It does not replace or retune the earlier run.

## Source findings

The official [EgoViz-120 dataset card](https://huggingface.co/datasets/humaidtech/EgoViz-120)
and [Hugging Face storage bucket](https://huggingface.co/buckets/humaidtech/EgoViz-120)
state CC BY 4.0, 5,392 clips, 12 categories, 180 capture-session `group_id`s,
and 7.25 TB total. Each MCAP contains synchronized egocentric/wrist video and
three IMUs on one clock. The card says a `group_id` is a capture session with
the same worker, site and lighting, and recommends splitting on that ID. It
does not establish that one worker cannot appear in multiple sessions, so
participant-level independence across groups remains unknown.

The publisher's `/action` annotations are generated by Gemini from the
ego-left video and are explicitly not human verified. They are not used as
targets or to select windows in this plan. The task target is the exact shared
clock interval, and the dataset contains no audio stream. This is a narrow
video-plus-sensor task, not a four-modality result.

## Fixed task and selection

For a two-second wrist-left video query sampled into eight frames, choose which
of four six-channel wrist-left IMU windows came from that same two-second
interval. Distractors come from the same clip at least three seconds away. The
matching target is timestamp identity, not the publisher's action prediction.
This directly tests whether frozen video and sensor representations can match
an aligned temporal state; video-only, sensor-only, shuffled-video and
permuted-option controls remain mandatory.

The fresh plan was generated from the official 871 kB `index.parquet` (SHA-256
`c83126637cc24a7ac2b3600724b50cf9c53966b9b098acc57d5534e14ade1074`) and the
prior acquisition manifest (SHA-256 recorded in the JSON manifest). It excludes
every group in the prior 16-file pilot, uses one clip per group, requires clips
to be at least 15 seconds and each MCAP to be no larger than 1 GB, and reserves
each of the 12 categories in all three splits before balancing the remaining
slots by category and file size. A deterministic SHA-256 tie-break uses seed
`20261029`.

## Why a fresh scale-up is justified

The prior 8-development-session pilot reached 47.27% development Accuracy and
1.2773 NLL for the joint scorer, compared with 28.18% / 1.3863 for sensor-only
and 14.55% Accuracy after within-session video mismatch. Training Accuracy was
98.11%, a 50.84-point gap. This suggests the video contains correspondence
signal while showing strong overfit; it does not establish useful general
quality. The new 20-session development split is a bounded test of whether more
unique sessions improve that result. All prior validation IDs and source
sessions remain excluded.

## Execution gate and remaining uncertainty

At plan creation, C: had 5.24 GiB free. The new train/development media would
need about 9.07 GiB if retained together, before temporary decode files and
features. Do not start bulk acquisition at that free-space level. A later run
must either verify a safe disk reserve or use a tested one-file-at-a-time
extractor that hashes and validates each download before releasing only its own
temporary raw file. No GPU use is required for planning; the live Orbitune
process remains untouched. Current RTX 3080 VRAM is heavily occupied, so the
follow-up should use CPU extraction unless a live resource check shows safe
GPU capacity.

Before fitting, verify each file's SHA-256 and MCAP CRC, confirm the actual
shared-clock window count, split membership and source IDs, and record the
exact VideoPrism/MOMENT revisions. Keep the architecture, task, sampling rule,
seed and selector fixed. Report group-level uncertainty and treat session
holdout as distinct from participant holdout. Do not evaluate the sealed split
until the candidate and checkpoint rule are frozen.

No model was trained, no quality claim was added, and no prior artifact or
checkpoint was changed in this follow-up.
